# 技能：需求接入（阶段1完整流程）

将任意形式的原始需求转化为结构化文档，同步完成工作量评估和伪需求扫描，输出明确的下一步指令。

用户输入的需求内容：$ARGUMENTS

## 完整处理流程

```
Step 0A  项目上下文感知（自动）
         扫描项目目录 → 识别技术栈、已有模块、历史需求
Step 0B  输入质量识别（自动）
         T1（一句话）→ 3个引导问题
         T2（零散）  → AI推断 + 最多3个澄清
         T3（半结构）→ 自动补全 + 最多2个确认
         T4（完整PRD）→ 直接结构化
Step 1   需求结构化
         自动补全字段，标注来源（✅自动 / ⚠️推断 / ❓缺失）
         6个核心字段完整性检查
         分配 need_id → docs/requirements/backlog/REQ-YYYYMMDD-XXX.md
Step 2   工作量联合评估
         业务维度5项 + 技术维度4项联合打分
         判定等级：S / M / L / XL
Step 3   伪需求扫描
         A 重复建设  B 价值存疑  C 逻辑冲突  D 技术可行性
         结论：🔴 阻断 / 🟡 警告 / 🟢 通过
Step 4   输出物推荐（扫描通过后）
         是否需要 Spec / UI原型 / 迭代计划
```

## 核心必填字段

| 字段 | 检查规则 |
|---|---|
| `need_id` | 自动分配，格式 REQ-YYYYMMDD-XXX |
| `title` | 不超过20字，包含动词+对象 |
| `priority` | P0 / P1 / P2，需说明定级理由 |
| `deadline` | 具体日期或明确里程碑 |
| `goal` | 必须可量化（含数字或可验证状态） |
| `acceptance` | 至少1条，格式："当[条件]时，系统应[行为]" |

## 工作量等级

| 等级 | 特征 | 工期 | 下一步 |
|---|---|---|---|
| S | 简单改动、≤1个页面、加字段 | 1-2天 | 直接 `/ai:code` |
| M | 新模块、2-4页面、新表 | 3-5天 | 先 `/ai:design` |
| L | 跨模块、5+页面、有技术风险 | 1-2周 | 先 `/ai:design` |
| XL | 整体重构、需拆分 | 4周+ | 先 `/ai:design` |

## 完成后明确告知下一步

- S 等级 → `/ai:code REQ-XXXXXXXX`
- M/L/XL 等级 → `/ai:design REQ-XXXXXXXX`
- 有 🔴 阻断项 → 解决后重新执行 `/ai:intake`
