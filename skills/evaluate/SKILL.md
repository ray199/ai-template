# 技能：需求评估

对已结构化的需求执行两项评估：
1. **伪需求扫描**：结合项目上下文判断需求是否值得做
2. **输出物推荐**：根据复杂度推荐需要产出哪些交付物

需求ID：$ARGUMENTS

## 处理流程

```
[Step 1] 加载项目上下文
         - 扫描代码库关键模块
         - 读取 docs/ 下设计文档和历史需求
         ↓
[Step 2] 伪需求扫描（4个维度）
         - A 重复建设：是否已有类似功能
         - B 价值存疑：ROI是否合理
         - C 逻辑冲突：是否与现有功能冲突
         - D 技术可行性：技术上是否可行
         ↓
[Step 3] 综合伪需求结论
         - 🔴 阻断 → 必须解决后才能继续
         - 🟡 警告 → 附建议，人工决定是否继续
         - 🟢 通过
         ↓
[Step 4] 输出物推荐（评估通过后）
         按复杂度矩阵判断：Spec / 原型 / 迭代计划
         ↓
[Step 5] 输出评估报告，等待人工确认
```

## 输出物推荐规则

### 复杂度判断维度
| 维度 | 低 | 中 | 高 |
|---|---|---|---|
| 涉及页面数 | 0-1 | 2-4 | 5+ |
| 涉及接口数 | 0-2 | 3-6 | 7+ |
| 数据库变更 | 无 | 改字段/加索引 | 新表/结构重构 |
| 影响已有功能 | 无 | 局部影响 | 跨模块/破坏性 |
| 工作量预估 | S(1-2天) | M(3-5天) | L/XL(1周+) |

### 推荐矩阵
| 复杂度 | Spec | 原型 | 迭代计划 |
|---|---|---|---|
| 低（全部低） | ❌ | ❌ | ❌ 直接技术设计 |
| 中（有1项中） | ✅ 建议 | 视UI复杂度 | ❌ |
| 高（有1项高） | ✅ 必须 | ✅ 建议 | ✅ 建议 |
| 跨迭代/XL | ✅ 必须 | ✅ 建议 | ✅ 必须 |
