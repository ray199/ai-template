# 原型必需性判定 - 详细评分维度

## 维度 1：功能类型（0-3 分）

| 功能类型 | 示例 | 分值 | 原因 |
|---|---|---|---|
| **纯后端/API** | 数据接口、定时任务、计算引擎 | 0 | 无 UI，不需原型 |
| **库/工具** | 工具类、SDK、算法优化 | 0 | 无 UI，不需原型 |
| **简单表单** | 登录、注册、简单增删改查 | 1 | UI 简单，文字描述足够 |
| **复杂表单** | 多步骤表单、权限配置、高级搜索 | 2 | 涉及多个交互，需简单示意 |
| **页面流程** | 完整业务流程（订单→支付→物流） | 3 | 多页面跳转，强烈需要可视化 |
| **数据大屏** | 统计分析、可视化仪表盘 | 3 | 布局复杂，必需原型 |
| **移动端应用** | 手机应用、响应式设计 | 3 | 交互密集，必需原型 |

## 维度 2：复杂度（0-3 分）

| 复杂度指标 | 0 分 | 1 分 | 2 分 | 3 分 |
|---|---|---|---|---|
| **页面数** | 0-1 页 | 2-3 页 | 4-6 页 | 7+ 页 |
| **功能点** | 1-2 个 | 3-5 个 | 6-10 个 | 11+ 个 |
| **交互流程** | 单线性 | 简单分支 | 多分支 | 复杂非线性 |
| **状态管理** | 无状态 | 简单状态 | 多状态转移 | 复杂状态机 |

## 维度 3：涉众（0-2 分）

| 涉众类型 | 分值 | 说明 |
|---|---|---|
| 仅开发团队内部沟通 | 0 | 技术人员能理解文字描述 |
| 需要与产品/设计沟通 | 1 | 非技术人员需要看到可视化 |
| 需要与最终用户沟通 | 2 | 必须展示给用户看以获得反馈 |

## 维度 4：验收标准（0-2 分）

| 验收标准特征 | 分值 | 示例 |
|---|---|---|
| 纯功能性验收（"支持查询"） | 0 | 无需原型 |
| 包含流程验收（"支持三步审批流"） | 1 | 需要简单流程图 |
| 包含 UI 验收（"菜单布局如下"或"需要日期选择器"） | 2 | 需要原型确认 |

## 总分判定

```
总分 ≤ 2     → 不需要原型（纯业务逻辑/后端 API）
3-6 分       → 可选原型（简单 HTML+示意图）
7-9 分       → 推荐原型（可交互的 HTML 或 Figma）
≥ 10 分      → 必需原型（完整交互原型）
```

## 原型形式选择细则

```
分数 3-4 → 低保真草图（仅快速概念验证，成本最低）
分数 5-7 → 复杂流程：HTML 可交互；否则 Figma 设计稿
分数 ≥ 8 → 涉众含最终用户：HTML 完整可交互；否则 Figma + HTML 混合
```
