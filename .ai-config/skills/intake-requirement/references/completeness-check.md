# 需求完整性检查规则

## Step 1 完整性检查（结构化阶段）

### 核心必填字段（所有等级都需要）

| 字段 | 检查规则 | 来源 |
|---|---|---|
| `need_id` | 自动分配（格式 REQ-YYYYMMDD-XXX） | AI 自动 |
| `title` | 不超过 20 字，包含动词 + 对象 | 用户输入 |
| `priority` | P0 / P1 / P2，需说明定级理由 | 用户输入/推断 |
| `deadline` | 具体日期或明确的里程碑（不接受"尽快"） | 用户输入/推断 |
| `goal` | 必须可量化（有数字或可验证的状态），至少 1 条 | 用户输入/推断 |
| `acceptance` | 至少 1 条验收标准，格式："当 [条件] 时，系统应 [行为]" | 用户输入 |

> 这 6 个字段是 Step 1 必须项，缺失任何一个都必须通过澄清问题补充。

### 辅助字段（基于来源类型和质量等级）

| 字段 | from_prd | from_verbal | 检查规则 | 自动补全 |
|---|---|---|---|---|
| `background` | 必填 | 必填 | 至少说明业务场景和当前问题 | ⚠️ 可推断 |
| `scope.in` | 必填 | 必填 | 列出本次包含的功能 | ❓ 不可 |
| `scope.out` | 必填 | 必填 | 列出不包含和留待后续的部分 | ❓ 不可 |
| `tech_constraints` | 必填 | 可选 | 技术栈 + 依赖系统 + 兼容性要求 | ✅ 自动 |
| `提需人` | 必填 | 必填 | 姓名 + 角色 | ⚠️ 推断自消息来源 |

> 自动补全字段都标注来源：✅ 自动 / ⚠️ 推断 / ❓ 缺失

## Step 2 工作量评估的输出物质量规则

### 需求分析师评估质量检查

| 检查项 | 合规条件 |
|---|---|
| 业务维度 5 项均已评分 | 每项 1-3 分，且已说明关键影响 |
| 得分在 5-15 范围内 | 5 项分数之和应在此范围 |
| 关键影响说明充分 | 3 分项必须解释为什么是高复杂度 |

### 架构师评估质量检查

| 检查项 | 合规条件 |
|---|---|
| 技术维度 4 项均已评分 | 每项 1-3 分，且已说明关键风险 |
| 得分在 4-12 范围内 | 4 项分数之和应在此范围 |
| 关键风险说明充分 | 3 分项必须说明技术风险是什么 |

## Step 3/4 输出物完整性检查（按工作量等级）

### S 等级（轻量版）

**必填字段（6 个）**：need_id + title + priority + deadline + goal (1 条) + acceptance (1 条)

| 检查项 | 合规条件 |
|---|---|
| 字段完整性 | 6 个字段全部非空 |
| 格式合规 | priority 为 P0/P1/P2，deadline 为日期，goal 可量化，acceptance 有"当...时，系统应..." |

通过：所有项 ✅ → 直接进入 /pg:code

### M 等级（标准版）

**必填字段（10 个）**：S 全部 + background + scope.in + scope.out + tech_constraints + acceptance (≥2 条) + goal (1-3 条)

| 检查项 | AI 检查 | 人工确认 |
|---|---|---|
| 字段完整性 | ✅ 10 个字段非空 | ✅ 逻辑一致（目标与验收对应） |
| 格式合规 | ✅ goal 可量化，acceptance 格式正确 | ✅ 业务逻辑准确 |
| 范围清晰 | ✅ 包含 + 不包含都有 | ✅ 边界明确，不存在歧义 |

通过：AI ✅ + 人工 ✅ → 进入 /pg:code

### L 等级（完整版）

**必填字段（15 个）**：M 全部 + stakeholders + non_functional + risks + tech_sketch + acceptance (≥3 条) + 可选 prototype_link

| 检查项 | AI 初检 | 人工终审 |
|---|---|---|
| 字段完整性 | ✅ 15 个字段非空 | ✅ stakeholders 完整（提需人 / 负责人 / 影响方） |
| 技术思路质量 | ✅ tech_sketch 存在 | ✅ 架构思路与现有代码库一致 |
| 风险识别 | ✅ risks 至少 1 项 | ✅ 应对方案切实可行 |
| 非功能需求 | ✅ non_functional 非空 | ✅ 性能/安全/兼容性要求可测试 |
| 原型匹配 | ✅ 涉及前端时 prototype_link 非空 | ✅ 原型与需求描述一致 |

通过：AI ✅ + 人工 ✅ → 进入 /pg:design

### XL 等级（超大型，需拆分）

**必填字段**：L 全部 + iteration_plan + milestones + prototype_link（前端必须）

| 检查项 | AI 初检 | 人工终审 | 团队评审 |
|---|---|---|---|
| 拆分合理性 | ✅ 子需求独立交付 | ✅ 拆分粒度合适 | ✅ 整体方向正确，无遗漏 |
| 里程碑明确 | ✅ milestones 有时间节点 | ✅ 各阶段目标清晰 | ✅ 资源分配可行 |
| 依赖梳理 | ✅ 子需求间依赖明确 | ✅ 实现顺序合理 | ✅ 并行/串行已确认 |

通过：AI ✅ + 人工 ✅ + 团队 ✅ → 拆分后的每个子需求各自走完整流程

## AI 自动检查规则（用于 Step 1 和 Step 3/4）

### 字段存在性检查
```
FOR each 必填字段 in 当前等级 DO
  IF 字段值为空或未提及 THEN
    输出澄清提示 + 关键问题说明
  ELSE
    继续检查格式
  END IF
END FOR
```

### 格式合规性检查
```
IF title 长度 > 20 字 OR 不含动词 THEN 标红
IF priority NOT IN [P0, P1, P2] THEN 标红
IF deadline 不是日期格式且不是明确里程碑 THEN 标红
IF goal 不含数字且不可验证 THEN 标红
IF acceptance 不符合"当...时，系统应..."格式 THEN 标红
```

### 逻辑一致性检查（M 级及以上）
```
IF goal 和 acceptance 不对应 THEN 警告
IF scope.in 和 scope.out 有重叠 THEN 错误
IF tech_sketch 中提到的模块与影响面评估不一致 THEN 警告
```
