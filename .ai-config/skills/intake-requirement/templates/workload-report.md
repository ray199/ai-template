# 工作量评估报告样例

> Step 2 输出。展示给用户确认评估等级。

```markdown
# 工作量联合评估报告

- **need_id**: REQ-XXXXXXXX
- **需求标题**: [标题]
- **评估时间**: YYYY-MM-DD

---

## 一、业务维度评估（需求分析师）

| # | 维度 | 评估 | 得分 |
|---|---|---|---|
| 1 | 涉及页面数 | 3 个页面（权限列表/编辑/分配） | 2 |
| 2 | 涉及接口数 | 6 个接口 | 2 |
| 3 | 数据库变更 | 新增权限表 + 关联表 | 3 |
| 4 | 影响已有功能 | 修改用户模块权限逻辑 | 2 |
| 5 | 数据迁移 | 无 | 1 |
| | **业务总分** | | **10** |

---

## 二、技术维度评估（架构师）

| # | 维度 | 评估 | 得分 |
|---|---|---|---|
| 1 | 架构变更 | 权限模块与用户模块跨模块整合 | 3 |
| 2 | 引入新技术 | 仅使用现有 Spring Security | 1 |
| 3 | 性能/并发 | 权限查询不高频，无特殊要求 | 1 |
| 4 | 安全/权限 | 涉及核心鉴权逻辑变更 | 3 |
| | **技术总分** | | **8** |

---

## 三、综合判定

- **基础等级**：业务分 10 + 技术分 8 → M 等级
- **兜底规则检查**：安全/权限涉及核心鉴权 → 触发"核心业务流程"规则 → **升级为 L**
- **最终等级**：**L（1-2 周）**
- **升级理由**：基础判定为 M，但安全/权限涉及核心鉴权逻辑，按兜底规则升级为 L

---

## 四、推荐输出物规范

根据 L 等级，需求文档需要：
- ✅ 完整版需求文档（15 个必填字段）
- ✅ 技术思路骨架（架构影响 + 关键决策点）
- ✅ UI 原型（涉及 3 个新页面）
- ❌ 迭代拆分计划（不需要）

**当前需求文档缺失字段**（需补充）：
- [ ] stakeholders - 干系人列表
- [ ] non_functional - 非功能需求（性能要求等）
- [ ] risks - 已知风险点
- [ ] tech_sketch - 技术思路骨架

补充示例：

## 干系人（stakeholders）
- 提需人：[名字]
- 技术负责人：[名字]
- 影响方：权限管理者、系统管理员

## 非功能需求（non_functional）
- 性能：权限查询 <100ms
- 兼容性：支持已有的 Chrome/Safari/Edge
- 安全性：权限变更需审计日志

## 风险点（risks）
- 风险：权限粒度过细导致管理复杂
  影响：中等
  应对：提供权限模板，简化配置

## 技术思路骨架（tech_sketch）
受影响模块：user、permission（新）、auth（改）
初步架构思路：
- 新增 permission 模块，定义权限和角色
- 在 user 模块中添加 role_permission 关联表
- auth 模块集成权限检查
关键决策点：
- 权限粒度：API 级别（而非页面级别）
- 权限缓存：使用 Redis 缓存用户权限列表，更新后 5 秒内生效
```
